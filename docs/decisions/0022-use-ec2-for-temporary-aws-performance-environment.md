# ADR 0022: Use EC2 for a temporary AWS performance environment

**Date:** 2026-08-27

## Status

Superseded in part by [ADR 0023](0023-prioritize-low-cost-ec2-performance-proof.md).

ADR 0023 replaces the instance sizing and its benchmark-isolation rationale. This ADR
remains the historical record of the original five-node EC2 decision, network
boundary, root-only storage, SSM operator path, and timezone-aware scheduler.

## Context

The first AWS topology was proven end to end with ECS Fargate, RDS PostgreSQL,
ElastiCache Serverless Valkey, Amazon MQ RabbitMQ, and an ALB. Its normal destroy
removed the Terraform-managed resources. Amazon MQ and the other managed resources
make that topology too expensive to leave running or recreate repeatedly for short
backend performance experiments.

The next experiment needs separate resource domains for the application tier, broker,
cache, database, and load generator. It must keep the existing immutable GHCR image,
migration bundle, health checks, RabbitMQ processing, Redis rate limit, PostgreSQL
persistence, and deterministic smoke semantics. It is deliberately not a production
HA deployment.

## Alternatives considered

1. Recreate the managed ECS/RDS/ElastiCache/Amazon MQ/ALB topology for every test.
   It has already proven value, but Amazon MQ imposes the dominant fixed cost.
2. Run all containers on one EC2 instance. This is cheapest but cannot isolate the
   resource use of the application, broker, database, cache, and k6 generator.
3. Use five EC2 nodes with containerized runtime services and HAProxy on the app
   node.
4. Use private subnets with a NAT gateway or SSM interface endpoints. This is a more
   conventional egress boundary but adds a fixed network cost that can rival the
   intended experiment savings.
5. Use a public ALB or Elastic IP for ingress. Neither is required when k6 runs in
   the VPC and SSM is the operator path.
6. Use fixed-UTC EventBridge cron or a host-level cron for operating hours. Both
   require manual DST treatment.

## Decision

Create a separate `infra/aws-ec2-performance/` Terraform root for five ordinary,
single-AZ Amazon Linux 2023 x86_64 EC2 instances:

- `app`: one `m7i.large` running HAProxy and two `PulseFlow.Api` containers;
- `rabbitmq`: one `m7i.large` running RabbitMQ;
- `redis`: one `t3.small` running Redis;
- `postgres`: one `m7i.large` running PostgreSQL; and
- `loadgen`: one `m7i.large` running k6.

Use static private IPv4 addresses in the VPC for all service-to-service traffic.
Security groups permit only loadgen-to-HAProxy HTTP and app-to-dependency ports.
Nodes have no public inbound rule, SSH key, bastion, ALB, or Elastic IP. They have
auto-assigned public IPv4 while running strictly for required outbound HTTPS egress;
the address is released when the node stops. Systems Manager Run Command is the sole
operator path.

Use only encrypted gp3 root volumes, with Docker named volumes for stateful container
data. Do not add EBS volumes, RDS, ElastiCache, Amazon MQ, ECS/Fargate, a NAT gateway,
or another managed runtime service.

The same shared read-only GHCR secret used by the managed AWS proof is reused. Runtime
PostgreSQL and RabbitMQ credentials are generated by Terraform, stored in Secrets
Manager, read only by the role that needs them, and treated as sensitive local
Terraform state.

EventBridge Scheduler invokes the EC2 StartInstances and StopInstances APIs on
weekdays at 08:00 and 17:00 in `Europe/Warsaw`, with no flexible window. AWS evaluates
the timezone and DST behavior. The initial Terraform apply confirms host bootstrapping
then stops all nodes; an explicit SSM-controlled deployment runs dependencies,
migrations, two API replicas, readiness, k6 smoke verification, and cleanup.

## Consequences

- Repeated short experiments avoid the managed Amazon MQ/ALB/RDS/ElastiCache fixed
  floor and isolate the main component resource domains.
- Four ordinary `m7i.large` nodes remove T-family CPU-credit behaviour and
  `m7i-flex` CPU-performance scaling from the primary experiment inputs. Redis begins
  on the smaller burstable type because it stores only rate-limit state; a sustained
  Redis result may justify resizing it.
- The environment is portable at the runtime layer but AWS-specific in provisioning,
  SSM, security groups, and scheduler resources.
- Stopping removes EC2 compute and temporary public-IPv4 cost, not root EBS or secret
  storage cost. A price review is still mandatory before every real plan.
- Stateful container data is intentionally disposable when Terraform destroys the
  nodes. Back up evidence before destroy if it is worth retaining.
- The shared GHCR secret means an explicit complete cleanup in one AWS environment
  must not delete it while the other environment is still in use.

## Intentionally deferred

- A real plan/apply and an observed EC2 lifecycle proof.
- A measured deployed bottleneck, component-level metrics/log collection, and a
  before/after optimisation conclusion.
- HA, replication, backups, production ingress/egress, remote Terraform state,
  restricted post-bootstrap RabbitMQ permissions, and public HTTPS/domain access.
- A multi-architecture GHCR image and a Graviton EC2 comparison.
